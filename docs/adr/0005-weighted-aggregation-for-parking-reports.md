# 0005 — เก็บรายงานที่จอดทุกใบบน D1 และรวมผลแบบถ่วงน้ำหนักตามเวลา (แทนการใช้ใบล่าสุด)

**สถานะ**: Accepted — แทนที่ส่วน aggregation ของ [0002](0002-crowdsourced-parking-checkin-for-mvp.md) (ส่วนอื่นของ 0002 เช่น rate limit / geofence ยังใช้ตามเดิม)

## บริบท

ADR 0002 เลือกใช้ "รายงานล่าสุดใบเดียว" เพราะตอนนั้นยังไม่มีข้อมูลจริงพอจะ tune สูตรถ่วงน้ำหนัก และ
timeline ก่อน demo สั้นเกินไป โดยเขียนไว้เองว่า *"ถ้าปริมาณ user รายงานจริงมากพอในอนาคต ควร revisit"*

สิ่งที่ทำให้ต้อง revisit เร็วกว่านั้น ไม่ใช่ปริมาณข้อมูล แต่เป็นพฤติกรรมที่ผิดตั้งแต่มีคนที่สองมารายงาน:

1. **รายงานใหม่ทับของเก่าเสมอ** — implementation เก็บ KV คีย์เดียวต่อลาน (`latest:{zone_id}`)
   ความเห็นของคน 5 คนใน 30 นาทีจึงเหลือความเห็นของคนที่กดคนสุดท้ายเพียงคนเดียว ไม่ใช่ภาพรวม
2. **คนกดพร้อมกันแล้วข้อมูลหาย** — การเขียน KV เป็น read-modify-write ไม่มี atomic write
   สองคนที่รายงานลานเดียวกันในเวลาไล่เลี่ยกันจะเหลือรอดใบเดียวแบบเงียบๆ
3. **ความเห็นแต่ละคนไม่ตรงกันโดยธรรมชาติ** — "เบาบาง/ปานกลาง/หนาแน่น" เป็นดุลพินิจส่วนตัว
   การเชื่อคนล่าสุดคนเดียวจึงแกว่งตามคนที่บังเอิญกดล่าสุด ไม่ใช่ตามสภาพจริงของลาน

ข้อ 1-3 ไม่ได้หายไปเองเมื่อมีข้อมูลมากขึ้น — มันแย่ลงตามจำนวนคนที่ใช้งาน

## การตัดสินใจ

**ย้ายรายงานที่จอดจาก KV ไป D1** (migration `0011_parking_reports.sql`) เก็บหนึ่งแถวต่อหนึ่งรายงาน
ด้วยเหตุผลชุดเดียวกับที่ README เขียนไว้เรื่อง "ทำไม user data ถึงอยู่บน D1 ไม่ใช่ KV": KV ไม่มี
atomic write, query ไม่ได้, และการอ่านหลายใบต้องใช้ `list` ซึ่งเป็นโควตาที่เคยทำ production ล่ม
(24 ส.ค. 2569) ส่วน D1 insert เป็น atomic และอ่านทุกลานได้ในคำถามเดียว

**รวมผลด้วยเสียงข้างมากถ่วงน้ำหนักตามอายุของรายงาน**:

1. ดึงรายงานของลานนั้นที่อยู่ในกรอบเวลา (ค่าเริ่มต้น 30 นาที)
2. ให้น้ำหนักแต่ละใบแบบเชิงเส้นตามอายุ — เพิ่งรายงาน ≈ 1, ใกล้ครบกรอบเวลา ≈ 0
3. รวมน้ำหนักตามสถานะ แล้วเลือกสถานะที่ได้น้ำหนักรวมมากที่สุด (เสียงเท่ากันตัดสินด้วยใบที่ใหม่กว่า)
4. ไม่มีรายงานในกรอบเวลา → `baseline_status` เหมือนเดิม
5. `source` ยังคงบอก `live_report` / `baseline_estimate` เสมอ และเพิ่ม `sample_size` กับ `agreement`

ยังคง **ไม่มี reporter reputation** ตาม 0002 — ความน่าเชื่อถือรายบุคคลยังไม่มีข้อมูลพอจะคำนวณ
แต่มีการจ่ายเหรียญโบนัสเมื่อรายงานถูกคนถัดไปยืนยัน ซึ่งเป็นแรงจูงใจ ไม่ใช่ตัวถ่วงน้ำหนัก

## ผลที่ตามมา

- รายงานหลายใบมีผลจริงทั้งหมด คนกดพร้อมกันไม่มีใครหาย และการกดมั่วครั้งเดียวไม่พลิกทั้งลานอีกต่อไป
- ยังพลิกตามสภาพจริงได้ทัน เพราะรายงานเก่าจางลงตามเวลา รายงานสดจึงชนะรายงานเก่าที่ใกล้หมดอายุ
- ตารางโตขึ้นเรื่อยๆ เพราะไม่มี TTL แบบ KV แล้ว — เก็บกวาดด้วย cron รายวัน โดย**ตั้งใจเก็บ 30 วัน
  ไม่ใช่ 30 นาที** เพราะประวัติย้อนหลังคือวัตถุดิบเดียวที่จะสร้าง baseline ตามช่วงเวลาได้ในอนาคต
- อ่านสถานะทุกลานใช้ 1 query (ไม่ใช่ 1 ต่อลาน) — ยังไม่แตะโควตา `list` ของ KV เลยตามกฎในREADME
- `agreement` กับ `sample_size` พร้อมใช้แล้วใน API แต่ยังไม่มี UI ไหนแสดง — ตั้งใจแยกเป็นคนละงาน
- **ข้อจำกัดที่ยังอยู่**: ลานที่มีคนรายงานน้อยยังตัดสินจากรายงานใบเดียวอยู่ดี การถ่วงน้ำหนักช่วยได้
  ต่อเมื่อมีหลายใบ — ส่วนนี้แก้ด้วยการเพิ่มจำนวนรายงาน (จุดถามตอนขาออก) ไม่ใช่ด้วยสูตร
