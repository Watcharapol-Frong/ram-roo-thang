# 0004 — บริการ/ขั้นตอนราชการ (Service FAQ) เป็นข้อมูล curated แยกจาก Community POI (deferred)

**สถานะ**: Accepted (โครงสร้างข้อมูลเท่านั้น — POI ยังไม่เริ่มพัฒนา)

## บริบท

ต้องการให้ chatbot ตอบคำถามได้กว้างขึ้นกว่าแค่ตึก/ที่จอดรถ 2 แบบที่ต่างกัน:

1. **คำถามเชิงขั้นตอนราชการ** เช่น "ยื่นขอใบเช็คเกรดได้ที่ไหน ทำยังไง" — เป็นข้อเท็จจริงคงที่ที่มหาวิทยาลัยกำหนดตายตัว ไม่เปลี่ยนบ่อย
2. **คำถามเชิงความสนใจ** เช่น "หิวข้าว มีร้านข้าวมันไก่ที่ไหนบ้าง" — ต้องอาศัยความรู้จากผู้ใช้จริงในพื้นที่ (ระบบรู้แค่ว่าอาคารไหนเป็นโรงอาหาร แต่ไม่รู้ว่าข้างในมีร้านอะไรบ้าง) เหมาะกับข้อมูลที่มาจาก community มากกว่าทีมกรอกเอง

ทั้งสองแบบต่างจาก `BASELINE_DATA` เดิม (building/parking_zone) ตรงที่ "ใครเป็นคนกรอกข้อมูล" และ "ต้องมี moderation หรือไม่" จึงจำเป็นต้องแยกโมเดลข้อมูลออกจากกันตั้งแต่แรก แม้จะยังไม่ implement ทั้งคู่เต็มรูปแบบตอนนี้

## การตัดสินใจ

แยกเป็น 2 เส้นทางที่ชัดเจน:

**`service`** — เดินตาม lifecycle เดียวกับ `building`/`parking_zone` ทุกประการ: ทีมกรอกข้อมูลไว้ล่วงหน้าด้วยมือ เก็บใน `BASELINE_DATA` KV เดิม (key `service:{service_id}`) ไม่มี user ทั่วไป submit เอง จึงไม่ต้องมี moderation workflow ใช้ `worker/src/data.js` (`getServiceByKey`, `listServices`) และต่อเข้า `retrieveContext` ใน `worker/src/ai.js` แบบเดียวกับ building — ตอบผ่าน Flex Message ที่ `worker/src/line.js` (`generateServiceFlexMessage`) พร้อมปุ่มนำทางไปอาคารถ้ามี `building_id` ผูกไว้

ข้อมูลจริงยังไม่ถูกกรอก (`data/baseline-dataset.json` มี `"services": []`) — **ห้ามใส่ข้อมูลที่เดา/ไม่ยืนยัน** เอง เพราะเป็นข้อเท็จจริงทางราชการที่ผิดแล้วมีผลกระทบจริงกับผู้ใช้ ต้องรอทีมกรอกด้วยข้อมูลที่ตรวจสอบแล้วเท่านั้น ระหว่างนี้ AI ต้องตอบว่าไม่มีข้อมูลเมื่อไม่ match อะไรเลย เหมือนที่ทำกับ building ที่ยังไม่มีอยู่ใน dataset (MVP-SPEC §8)

**`poi`** — **ยังไม่เริ่มพัฒนา** วางแผนไว้ว่าจะเป็นจุดที่ user ทั่วไป submit เอง (ร้านอาหาร ฯลฯ) แล้วต้องผ่าน workflow ตรวจสอบ/อนุมัติก่อนถึงจะโผล่ในคำตอบของ AI ได้ (กันข้อมูลเท็จ/สแปม) — นี่คือ "Community POI + Moderation" ที่ระบุไว้ใน `MVP-SPEC-for-Dev.md` §9 Out of Scope อยู่แล้ว ไม่ใช่ของใหม่ ตอนนี้มีแค่ placeholder ว่างใน `data/baseline-dataset.json` (`"poi": []`) เพื่อจอง shape ไว้ล่วงหน้า **ไม่มี KV namespace, endpoint, submission form, หรือ moderation logic ใดๆ อยู่ในโค้ดตอนนี้** ต้องคุยยืนยัน scope/ออกแบบ workflow การอนุมัติก่อนเริ่ม implement จริง

## ผลที่ตามมา

- `service` ใช้โครงสร้าง/โค้ดเดิมได้ทันที ความเสี่ยงต่ำ แค่รอทีมกรอกข้อมูลจริง
- `poi` ยังเป็นแค่เอกสาร + placeholder เฉยๆ — ต้องมีรอบออกแบบแยกต่างหากอย่างน้อยเรื่อง: ใครอนุมัติ, อนุมัติผ่านช่องทางไหน (ในเมื่อ Admin Portal ก็อยู่ใน Out of Scope เหมือนกัน), และจะกัน spam/เนื้อหาไม่เหมาะสมยังไงก่อนเปิดให้ submit จริง
- ถ้าในอนาคตพบว่า `service` เริ่มมีคนอยากช่วยเพิ่มข้อมูลเองเยอะขึ้น (ไม่ใช่แค่ทีม) ให้พิจารณาย้ายไปใช้โมเดลเดียวกับ `poi` แทน ไม่ใช่ผสมสองแบบไว้ในที่เดียว
